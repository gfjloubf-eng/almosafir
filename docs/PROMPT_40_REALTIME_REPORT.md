# تقرير P40 «النبض الحي» — إشعارات لحظية SignalR + تقوية تثبيت سطح المكتب

**التاريخ:** 2026-08-31 · **الطلب:** «ما الذي يحتاجه تطبيق الديسكتوب ليخزّن ويتصل بالسيرفر وتحديثات مباشرة ويكون أقوى — وهل يحتاج نت؟»

## ما الذي أُضيف

| القطعة | الملف | الدور |
|---|---|---|
| مركز SignalR | `src/AlMosafer.Web/Hubs/AppHub.cs` | قناة WebSocket؛ كل اتصال ينضم لمجموعة `user-{id}` الخاصة به — لا بثّ يعبر لمستخدم آخر. محروس بـ`[Authorize]` (نفس كوكي الجلسة). |
| مزخرف البث | `src/AlMosafer.Web/Services/RealtimeNotificationServiceDecorator.cs` | يلتفّ حول `NotificationService` **دون تعديله**: بعد حفظ الإشعار بالقاعدة يبثّ نبضة لحظية. فشل البث لا يُسقط الحفظ أبداً. |
| عميل المتصفح | `wwwroot/lib/signalr/signalr.min.js` | الإصدار الرسمي `@microsoft/signalr@8.0.7` — **موفَّد محلياً** لأن CDNs محجوبة عن بيئة البناء (وُفِّد من npm registry الرسمي — SHA-256 موثّق في `README.txt` بجانب الملف + إشعارات الطرف الثالث). |
| منطق العميل | `wwwroot/js/realtime.js` | اتصال بـ`withAutomaticReconnect()` (يعود وحده عند رجوع النت)، تنبيه فوري عائم، وتحديث شارة الجرس. |
| شارة العدّاد | `_Layout.cshtml` | عدّاد أحمر بجانب «🔔 الإشعارات» + تحميل سكربتات اللحظية للمسجَّلين فقط. |
| عدّاد JSON | `NotificationsController.Count` | `/Notifications/Count` للقراءة الأولى عند فتح أي صفحة. |
| اختصارات التثبيت | `manifest.webmanifest` | ضغطة مطوّلة على أيقونة سطح المكتب تُظهر: الرحلات، حجوزاتي، الخطوط الداخلية، الإشعارات. |

## المعمارية — لماذا مزخرف (Decorator) بدل تعديل الخدمة؟

1. `NotificationService` يعيش في طبقة **Infrastructure** — حيادي عن الويب (Clean Architecture). جرّ SignalR إليه يكسر الاتجاه المعماري.
2. اختباراته تبنيه بـ`new NotificationService(dbContext)` مباشرةً — أي تغيير مُنشئ يكسرها.
3. الحل: التسجيل في DI يصير خدمتين: الأصلية باسمها + الواجهة تُحلّ عبر مصنع يغلّفها بالمزخرف. **صفر تعديل في الشيفرة القديمة وصفر تعديل في الاختبارات.**

## تدفق النبضة

```
حفظ إشعار في القاعدة (مصدر الحقيقة الدائم)
        │
        ▼
مزخرف البث ──فشل؟──▶ سجل تحذير ويكمل — لا شيء يضيع
        │ نجاح
        ▼
مجموعة user-{id} عبر WebSocket
        │
        ▼
المتصفح: تنبيه عائم + شارة العدّ تتحدث — بلا F5
```

## هل يحتاج «نت»؟ — الجدول الصادق

| السيناريو | إنترنت/اتصال بالخادم؟ | السبب |
|---|---|---|
| البحث عن رحلات / الحجز / الدفع | **نعم** | البيانات في قاعدة MySQL على الخادم؛ الحجز كتابة لا يصح اختراعها دون اتصال. |
| الإشعارات اللحظية (P40) | **نعم** | WebSocket حي بين المتصفح والخادم — ينقطع بانقطاع النت ويعود وحده عند رجوعها. |
| فتح التطبيق المثبَّت | **لا** | الغلاف (واجهة، أيقونات، CSS/JS المحلية) مخبأ في الجهاز عبر Service Worker. |
| صفحة انقطاع أنيقة | **لا** | `offline.html` تُعرض عند غياب الاتصال بدل خطأ المتصفح. |
| قراءة بيانات قديمة بلا نت | ليس بعد | مرحلة مستقبلية (تخزين قراءة محلي IndexedDB + مزامنة) — لن تُدَّعى قبل بنائها. |
| حجز بلا نت | **مستحيل مبدئياً** | الخادم وحده يؤكد المقعد ويكتب القاعدة — أي تطبيق يعدك بحجز «أوفلاين» يبيعك وهم تزامن لاحق. |

## حدود صادقة

- الملف المورَّد هو **الإصدار الرسمي نفسه** لكنه منسوخ في المستودع — أي ترقية أمنية مستقبلية تتطلب إعادة الوفادة يدوياً (موثّق SHA-256 للمطابقة).
- اللحظية تغطي **الإشعارات** حالياً (حجوزات/مدفوعات/رسائل تصل عبرها)؛ ترقية صندوق الدردشة نفسه من polling كل 15ث إلى دفع لحظي خطوة لاحقة على نفس المركز (`AppHub` جاهز لها).
- Push Notifications الحقيقية (تصل والتطبيق مغلق) تحتاج VAPID + HTTPS عام — خارج النطاق المحلي.

## التحقق

- CI على main هو الاختبار الوحيد المتاح (لا SDK محلياً في بيئة البناء) — يجب أن يبقى أخضر بـ90+ اختباراً دون أي تعديل عليها.
- يدوياً: سجّل دخول → افتح صفحتين → أنشئ فعلاً يولّد إشعاراً (حجز) → التنبيه والشارة يظهران فوراً في الصفحة الأخرى.
